# GameVault 总览 —— 平台与游戏想法、可行性、路线图

> 版本：2026-10 初稿（引擎矩阵为 2026-10 调研快照，引用时须按官方当前版本复核）
> 本文只给「想法 + 可行性判定 + 实现路径摘要」；详细设计在 `01..07` 各文档。

---

## 1. 平台定位与目标

**一句话**：sysou.com/game 是一个「即开即玩」的浏览器游戏展示平台 —— 每款游戏代表一种主流 Web
游戏技术栈，平台既是游戏站，也是 Web 游戏技术矩阵的展示橱窗。

### 1.1 产品目标

| 目标 | 说明 | 衡量 |
|---|---|---|
| 零门槛试玩 | 打开链接 3 秒内能开始玩第一关；不装客户端、不强制登录 | 首玩时长 P90 < 3s（4G） |
| 技术展示 | 每个游戏卡片标注引擎/语言/架构（Phaser·TS / Three.js·WebGPU / Godot·GDScript·WASM / Canvas·原生 TS），展示页有技术拆解区 | 每游戏 ≥ 1 篇「技术拆解」 |
| 可玩性沉淀 | 分数排行 + 成就，给回访理由 | 周活跃提交分数用户 |
| 可运营 | 管理台上传/下架/回滚游戏包，不重新部署平台 | 发布一个游戏 ≤ 10 分钟 |

### 1.2 非目标（MVP 明确不做）

- 不做 UGC（玩家自制游戏上传）——安全与内容审核成本高，二期以后再说
- 不做付费/内购/广告 —— 展示平台属性，不做营收
- 不做账号体系 —— 登录/权限全部走 `sysou-manage` 中心
- 不做原生客户端（iOS/Android App）—— Web 优先；Godot 引擎虽可出原生，但本平台只发布 Web 版

## 2. 平台层想法（P1–P6）

| # | 想法 | 说明 | 可行性判定 |
|---|---|---|---|
| P1 | **沙盒化即时试玩** | 游戏以静态包（HTML/JS/WASM/资源）形式托管，平台用 `<iframe sandbox>` 加载；同源自由调用平台 API，`allow-scripts allow-same-origin allow-pointer-lock allow-autoplay`，不给 `allow-top-navigation` | **高**。Poki/CrazyGames 同款模式被验证多年；难点在 COOP/COEP 头（见 §3 引擎矩阵，平台统一解决） |
| P2 | **游戏目录与展示详情** | 首页网格卡片（封面/引擎徽章/标签/最近高分），详情页 = 试玩 iframe + 介绍 + 技术拆解 + 排行榜 + 成就 | **高**。纯展示型页面，无技术风险 |
| P3 | **排行榜 + 成就** | 登录（sysou-manage JWT）后提交分数；Redis ZSET 维护实时榜 + 定期落库；每游戏若干成就（首次通关/高分/连击），服务端判定发放 | **高**。成熟方案；风险点 = 作弊，用服务端校验 + 限流 + 幂等 + 异常分数人工复核兜底（§01 文档） |
| P4 | **游戏发布管理台** | 管理员上传游戏 zip（含 `manifest.json`）→ 异步校验（结构/大小/manifest schema/内容安全扫描）→ 解压发布到版本目录 → 一键上架/下架/回滚 | **高**。静态包 + 校验管线，无需运行任何上传代码（红线：平台不执行玩家上传的代码） |
| P5 | **技术矩阵橱窗** | 游戏卡片带引擎/架构标签；详情页「技术拆解」区写清选型理由、性能手段、踩坑记录（与 `docs/design/03..07` 互链） | **高**。零运行时成本，纯内容工作，但最能体现平台差异化 |
| P6 | **轻量运营统计** | 每游戏 PV/试玩开始/时长/退出点/分数分布，事件走 `/api/telemetry` 批量上报，Redis + 每日聚合落库 | **中-高**。量小（个人站流量），单 VPS 足够；先做最小集（PV/开始/时长），其余按需 |
| P7 | **云存档（账号绑定）** | 登录用户存档存服务端（`user_save`，opaque JSON），换设备/换浏览器/清缓存不丢；游客 = 仅本地 localStorage 档；冲突 LWW-lite + 玩家显式裁决（01 文档 §5.2、02 文档 §4.4） | **高**。1 张表 + 2 个 API + 游戏桥接 ~40 行，单 VPS 负载可忽略；已从 08 文档 N3（默认不做）提升进 M3 |

**结论**：P1–P4 是 MVP 核心（M1–M2），P5 随各游戏文档产出，P6/P7 从 M3 起（P7 云存档与登录配套交付，
把「游客试玩 → 登录解锁分数/成就/存档」的成长路径补齐）。全部想法技术上无不可行项，
关键工程量在平台骨架（一次）+ 每款游戏（独立）。

## 3. 游戏层想法（A–E）与引擎选型

### 3.1 想法清单

| # | 游戏 | 品类 | 引擎/技术栈 | 一句话卖点 |
|---|---|---|---|---|
| A | **霓虹突袭（Neon Raid）** | 2D 横版自动射击 | **TypeScript + Phaser 4**（2026-04 正式发布，节点式 WebGL 渲染器） | 经典街机手感 + 霓虹视觉；Phaser 是 HTML5 2D 社区最大的引擎，代码驱动 |
| B | **方块狂奔（Cube Rush）** | 3D 无尽跑酷 | **Three.js r186**（WebGPURenderer，自动回退 WebGL2） | 低多边形 + 霓虹夜色，展示 WebGPU 在浏览器里的 3D 效果上限（个人项目量级内） |
| C | **地牢回声（Dungeon Echo）** | 像素俯视角地牢爬行 | **Godot 4.6 + GDScript → WebAssembly 导出** | 用「最接近完整游戏引擎」的路径做一个有存档/生成/战斗的完整游戏，展示 GDScript + WASM 路线 |
| D | **极速反应（Reflex Rush）** | 反应力挑战 | **原生 TypeScript + Canvas 2D，零依赖** | 无引擎、<50KB、秒开；既是 M1 首发游戏，也是「裸 Canvas 能做什么」的基准展示 |
| E | **弹珠对轰（Marble Duel）**（二期） | 实时 1v1 对战 | **原生 TS 客户端 + Spring WebSocket 服务端权威物理** | 展示「Web 也能做真·实时多人」：服务端 30Hz 权威仿真 + 客户端插值，反作弊天然（输入才上服务器） |

**组合逻辑**：五款游戏刻意覆盖「轻 → 重」的完整光谱 —— D（裸 Canvas，~30KB）→ A（2D 引擎，~4MB）→
B（3D 库，~15MB）→ C（完整引擎 WASM，~30MB）→ E（加一层服务端）。每加一档，玩家与读者都能看到
「加载体积/效果上限/开发效率」的权衡，这正是平台作为技术橱窗的核心叙事。

### 3.2 引擎选型矩阵（2026-10 调研快照，来源 + 日期见脚注）

| 维度 | Phaser 4 | Three.js r186 | Godot 4.6 Web | 原生 Canvas |
|---|---|---|---|---|
| 定位 | 2D 完整引擎（场景/物理/音频/输入） | 3D 渲染库（自组游戏逻辑） | 完整引擎（编辑器/场景/物理/动画）导出 WASM | 无引擎，手写一切 |
| 语言 | TS/JS | TS/JS | GDScript/C# | TS |
| 构建产物 | JS（WebGL） | JS（WebGPU/WebGL2） | HTML+JS+WASM+PCK | JS |
| 体积量级 | 引擎 ~1.5MB + 资源 | 库 ~700KB + 资源 | 引擎 wasm 20–35MB + 资源 | 自定（可 <50KB） |
| WebGPU | 无（WebGL） | **WebGPURenderer**：默认试 WebGPU，不支持自动回退 WebGL2 [1] | 无（WebGL2 路径，Web 渲染上限低于 Three.js/PlayCanvas） | 无 |
| 多线程 | 无 | 无（可自加 Worker） | 可选线程版需 **SharedArrayBuffer + COOP/COEP**；4.3 起单线程导出已修复完善 [2] | 可自加 Worker |
| 适用 | 2D 街机/平台/解谜 | 3D 展示/跑酷/飞行 | 完整度优先的 2D/3D 游戏 | 极简小游戏/教学 demo |
| 社区/文档 | 最大 HTML5 2D 社区 [4] | 最大 WebGL 库社区 [3][4] | 完整引擎社区，编辑器免费开源 | — |

**选型裁定**：
- A 用 Phaser 4（2026-04-10 GA，v4.2.1 为 2026-07 最新 [5]）——2D 代码驱动首选；注意 v4 是渲染器大重写，
  开发时跟随官方迁移指南，**不混用 v3 教程**。
- B 用 Three.js r186（2026-09 发布）[1]——WebGPURenderer 已可作为「现代替代 WebGLRenderer」，
  内置 WebGL2 回退 [1]，正好覆盖 Safari 等 WebGPU 弱环境。
- C 用 Godot 4.6 Web 导出 [2]——Web 端要求 WASM + WebGL2；默认发布**单线程构建**（不依赖 SAB），
  平台同时把 `/game/` 前缀加上 COOP/COEP 头（§02 文档），使可选的**线程版构建**也能跑。
- 不选 PlayCanvas/Babylon/Cocos/Defold：个人项目体量下 Three.js 覆盖 3D 需求且与 A/B 的 TS 技术栈连续；
  Cocos 偏移动端打包、PlayCanvas 引擎编辑器与本地迭代闭环不如 Godot 顺。
- 移动端策略：A/B/C 全部要求做触控操作（虚拟摇杆/滑动/屏幕按钮），D 天然触控；平台 H5 响应式布局。

### 3.3 各游戏可行性判定（摘要，细节在各游戏文档）

| 游戏 | 可行性 | 主要风险与对策 |
|---|---|---|
| A 霓虹突袭 | **高** | Phaser 4 新架构文档少 → 锁定 v4.2.x 跟官方迁移指南；音频自动播放策略 → 首次交互后开 AudioContext |
| B 方块狂奔 | **高** | WebGPU 兼容性分层（新 Chrome/Edge/Safari 有，部分安卓 WebView 无）→ WebGPURenderer 自动回退 WebGL2，效果降级可接受；性能靠 InstancedMesh + 视锥剔除 |
| C 地牢回声 | **中-高** | ① 首包 25–35MB 加载慢 → 加载进度 UI + 单线程构建（免 SAB 依赖）+ 预压缩（Brotli）；② Godot Web 音频需 .ogg → 统一转码；③ 引擎迭代快 → 锁定 4.6，升级走独立 PR 验证 |
| D 极速反应 | **很高** | 几乎无风险；价值在于 M1 周就跑通「开发 → 打包 → 管理台发布 → iframe 试玩 → 提分」全链路 |
| E 弹珠对轰 | **中（二期）** | ① 服务端权威仿真的网络抖动 → 30Hz tick + 客户端插值 + 重同步策略；② 单机 VPS 并发上限 → Redis pub/sub 横向扩展设计已备，先按单实例跑；③ 反作弊天然（只收输入），但需防输入洪泛（限流 + tick 预算） |

## 4. 总体架构（一图流）

```
                        https://sysou.com/game/
                                │
              sysou.com nginx（443，同一 server 块，/game/ 前缀）
        ┌────────────────────────┼──────────────────────────┐
        │                        │                          │
  /game/ 静态（平台前端）    /game/api/ → :8094        /game/g/<gameId>/<ver>/
  /var/www/gamevault/static/  平台后端 API（8094）       游戏静态包（iframe 加载）
                             ┌───────┴────────┐          /var/www/gamevault/games/
                             │ gamevault.jar   │
   中心 JWT(ES256) ←──┐     │ Java 21+Boot 3.4.5│
   sysou-manage(:8093)│     │ Spring Modulith  │
                      │     ├──────────────────┤
                      │     │ catalog / player │
                      │     │ leaderboard /    │
                      │     │ admin / telemetry│
                      │     ├──────────────────┤
                      │     │ JPA+Flyway → PostgreSQL db gamevault
                      │     │ Redis Streams Job + Redis(db3) 缓存/限流/ZSET 榜
                      └─────┤ WebSocket(M5：对战)
                            └──────────────────┘
```

要点：
- **游戏代码永远不跑在服务器上**——平台只托管静态文件 + 接收分数/遥测/管理操作（红线，见 CLAUDE.md）。
- 游戏 iframe 与平台**同源**（`/game/g/...`），游戏可直接 `fetch('/game/api/...')`；同时保留
  `postMessage` 协议作为跨域 CDN 化后的演进路径（`02` 文档）。
- `/game/` 前缀所有响应统一加 `Cross-Origin-Opener-Policy: same-origin` +
  `Cross-Origin-Embedder-Policy: require-corp`（COOP/COEP）：同源资源天然满足 require-corp，
  使 `SharedArrayBuffer` 在 iframe 内可用（Godot 线程版需要），且对其他游戏零副作用（`02` 文档详述）。

## 5. 路线图（里程碑）

| 里程碑 | 内容 | 产出 | 周期 |
|---|---|---|---|
| **M1** | 平台骨架：后端 Modulith 单体（catalog/player/admin 最小集）、Vue 目录页 + iframe 播放器、nginx `/game/` 挂载（含 COOP/COEP）、管理台上传-校验-发布；**游戏 D** 首发 | 可公网打开 `sysou.com/game/` 玩到「极速反应」 | ~3 周 |
| **M2** | 排行榜 + 成就 + 登录（sysou-manage 接入）；**游戏 A**（Phaser 4） | 登录提分、全服榜/周榜、成就解锁 | ~3 周 |
| **M3** | **游戏 B**（Three.js WebGPU）+ 运营统计最小集 + 云存档（P7，`user_save` + 存档 API + 游戏桥接）+ 技术拆解页规范 | 3D 游戏上线，PV/时长/分数分布，登录玩家跨设备存档 | ~4 周 |
| **M4** | **游戏 C**（Godot WASM）+ 大包加载优化（Brotli/预加载/进度）+ COOP/COEP 回归测试 | 完整引擎游戏上线 | ~4 周 |
| **M5**（二期） | **游戏 E**（WebSocket 对战）+ 房间/匹配 + 对战回放（可选） | 实时多人上线 | ~4 周 |
| **N1**（前瞻·触发制） | 原生游戏（非浏览器）下载发行：`game_build` 载体拆分 + `/game/dl/` 下载服务 + 客户端 SDK + 代码签名（08 文档） | 首个「Web 承载不足」的原生游戏立项 | ~2–3 周 |
| **N2**（N1 后按需） | 增量更新（binary diff / 资源分包）+ 启动自动更新 | 单包 >500MB 或月更 ≥1 次 | ~2 周 |

**依赖关系**：M1 是一切的地基（播放器协议 + 发布管线定稿后，游戏可按任意顺序并行开发）；
M2 的排行榜是 A/B/C 共用的；E 不阻塞任何一期内容。

## 6. 风险汇总（跨想法）

| 风险 | 影响 | 对策 |
|---|---|---|
| 个人 VPS 带宽/磁盘装不下多游戏大包 | C 游戏 30MB 首包 × 高流量时带宽告急 | 静态资源 30 天长缓存（M1 nginx 已备）；后续可把 `/game/g/` 挂 CDN（同源协议不变，postMessage 已预留） |
| 浏览器 COOP/COEP 头影响同域其他子站 | `/game/` 外不受影响（头只加在 `/game/` 前缀响应上） | 部署时 nginx `location ^~ /game/` 作用域隔离，上线前 `curl -sI` 实测各资源头 |
| 引擎版本快速迭代（Phaser 4.0 大重写 / Godot 4.x） | 教程与文档过时 | 锁定 minor 版本；升级单独 PR + 回归；文档矩阵标注快照日期 |
| 分数作弊 | 榜单公信力 | 服务端校验（分数边界/时间合理性）+ 限流 + 幂等 + 周榜滞后结算 + 异常分人工复核 |
| 移动端触控体验参差 | 差评集中在手机端 | 每游戏文档强制列触控方案；M1 起播放器内置「桌面/移动」提示 |

## 7. 非浏览器（原生）游戏的前瞻规划（摘要，全文见 08 文档）

当前 M1–M5 全部是**浏览器试玩**（02 文档的游戏包规范以「纯静态 + 浏览器执行」为前提）。但平台核心
（目录/详情/榜单/成就/遥测/管理台/认证）从设计上**与载体无关**——原生游戏需要的「发布、宣传、下载、
计分」四件事里，前三件中的两件半已经就绪，唯独**分发（下载 + 更新）要新增**。因此：**不为短期需求写代码，
但把结构提前留好**：

- **核心架构动作**：`game_version`（当前隐式 = web 版本）演进为「版本 + `game_build`（载体：
  web/windows/macos/linux）」——同一版本可多载体独立发布/回滚；V2 迁移 SQL 与回填脚本在 08 文档 §3。
- **零成本预留（N0，随 M1 落，≈0.5 天）**：`game.media` 字段（截图/预告片/外部商店链接，宣传面）＋
  详情 API 恒带 `builds[]` 形状 ＋ nginx `/game/dl/` 注释位置 ＋ 管理台「构建」Tab 占位。
- **N1 触发条件**（触发制，非排期）：出现一款具体「Web 承载不足」的自研游戏（包体 >500MB / 需要 Web
  给不了的画质 / 玩家要下载版）。最自然候选 = Godot 系大型项目（一套代码 web + 原生双出，05 文档选
  Godot 的隐含收益）。
- **刻意不做**：DRM/激活、云存档账号库（N3 默认不做）、第三方游戏分发（自研红线，需单独评审）。
- **最大现实约束**：个人 VPS 带宽——下载量触线强制上 CDN（URL 结构不变）；Windows/macOS 构建强制
  签名/公证才可发布（管理台闸门）。

## 脚注（调研来源，2026-10 抓取）

1. Three.js WebGPURenderer 官方文档（threejs.org/docs/pages/WebGPURenderer）：WebGPURenderer
   为「WebGLRenderer 的现代替代」，默认试 WebGPU、不支持时回退 WebGL2 后端；r186 于 2026-09-08 发布（GitHub releases）。
2. Godot 4.6 官方文档《Exporting for the Web》：Web 导出需 WASM + WebGL2；多线程需 SharedArrayBuffer
   并依赖服务端 COOP/COEP 头与跨源隔离；`progressive_web_app/ensure_cross_origin_isolation_headers` 选项；
   Godot 官方博客《Web Export in 4.3》：4.3 修复单线程导出（不再默认依赖 SAB）。
3. Three.js 官方定位：3D 渲染库（场景图/材质/相机/加载器/后处理），非完整引擎。
