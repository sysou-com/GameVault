# 07 · 游戏 E「弹珠对轰 Marble Duel」详细设计（WebSocket 实时对战 · 二期）

> 品类：实时 1v1 对战（空气曲棍球式弹珠）｜客户端：原生 TS + Canvas 2D｜服务端：**Spring WebSocket
> 权威仿真**（30Hz 固定 tick）｜平台接入：按 `02` 文档（包体小，静态托管不变）｜里程碑：**M5（二期）**｜
> 展示价值：「Web 也能做真·实时多人」——服务端权威 + 客户端插值 + 天然反作弊（服务器只收输入）

---

## 1. 游戏设计

### 1.1 核心玩法（单场 ~2 分钟）

- 俯视角长桌竞技场（Canvas 2D，1024×576），左右半场；中央一枚**弹珠 puck**（有摩擦，
  速度衰减 0.985/帧@60fps，服务端按 30Hz 换算）。
- 每玩家控制 1 枚**己方弹珠**（蓝/红），**摇杆式连续施力**（桌面：方向键/WASD 按住即加速，
  松手摩擦减速；移动：左半屏摇杆 + 右半屏备用）——类气垫球（air hockey）手感，规则更慢更策略：
  - 己方弹珠只能待在本半场中线 ± 20% 缓冲带内（出界推回 + 0.5s 硬直——防死守死贴）。
  - **进球**：把 puck 推进对方端点口袋（两端各 1 口袋，宽 140px）→ 进攻方 +1 分，puck 与双方弹珠复位。
  - 胜负：**先得 5 分**；单场 5 分钟未分胜负 → 比当前分，平局加赛 1 分钟（金球制）。
- 附加技巧：己方弹珠**贴住 puck 可以挡**（防守），连续进球 2 次触发「过载」（己方弹珠加速度 +20%，
  持续 5s）——给进攻节奏感。

### 1.2 计分（对接平台标准提分 API）

- 单场结束：胜者提交 `score = 500×(己方得分) + 200×(对方失分≤5) + max(0, 3000 - 用时秒)×10`，
  负者提交 0–300（按表现：扑救次数×50）。meta：`{ wins, losses, saves, durationMs }`。
  `score.range` 0–20000。成就：FIRST_WIN / WIN_3（三连胜，平台侧按历史提交记录判定）/ SAVE_10（单场 10 次成功扑救）。
- 「成功扑救」= 防守方半场 puck 速度 > 阈值时被挡回中线方向（服务端判定，遥测回传展示）。

### 1.3 房间与匹配

- M5 首发：**房间码制**（6 位码，创建者给链接/代码 → 对方输入加入 → 双 ready → 开局）——
  零匹配服务器复杂度，社交感强（朋友互刷）。
- 随机匹配（quick match）= M5 之后的可选增强（Redis List 排队 + 配对 Job），设计预留、不阻塞首发。

## 2. 技术架构

### 2.1 总体（单实例起步，架构留扩展缝）

```
浏览器 A（Canvas 渲染 + 摇杆输入）        浏览器 B
   │  WSS /game/api/duel/ws（nginx upgrade）   │
   └──────────────┬──────────────────────────────┘
                  ▼
        gamevault.jar（:8094，M5 激活 WebSocket 端点）
        ┌─────────────────────────────────────┐
        │ duel 模块（01 文档 §2 模块清单新增）    │
        │  RoomService（房间生命周期/ready/状态机） │
        │  TickEngine（30Hz 固定步长仿真调度）     │
        │  Physics（圆-圆/圆-墙碰撞，纯函数）      │
        │  Scoring（进球/扑救/胜负判定）           │
        └──────────────┬──────────────────────┘
                       ▼ 房间索引
                 Redis(db3): room:<code> → nodeId/状态摘要（单实例时仅做索引与重连恢复）
```

- **单 VPS 单 JVM 起步**（个人站量级足够：单进程 30Hz tick × 并发 200 房间 ≈ CPU < 5%）；
  多实例扩展缝：房间状态内存驻留节点内，Redis 存 `room:<code> → nodeId` 路由；扩容时引入
  Redis pub/sub 转发跨节点消息（协议不变，只改消息路由层）——**M5 不实现，仅留接口**。

### 2.2 通信协议（原生 WebSocket，JSON 帧；不走 STOMP——帧简单，少一层依赖）

**客户端 → 服务端**（只收这些，其余一律丢弃 + 计数告警）：

| op | 字段 | 说明 |
|---|---|---|
| `create` | `{ code? }` | 建房（code 缺省服务端生成 6 位）→ 回 `joined{code, seat:left}` |
| `join` | `{ code }` | 加入 → `joined{seat:right}` / `error{room_full\|not_found\|in_progress}` |
| `ready` | `{}` | 双方 ready → `start{seed, rules}` |
| `input` | `{ f:{x,y}, v }` | 摇杆力向量（服务端钳位 |f|≤1）+ 客户端帧序号 v；**≤30 次/秒**（限流，超了丢弃+计数） |
| `ping` | `{t}` | 心跳（3s 一次；服务端 10s 未收到 → 断线流程） |

**服务端 → 客户端**：

| op | 字段 | 说明 |
|---|---|---|
| `snapshot` | `{ v, t, p:[{x,y,vx,vy}×3], charge, overheat }` | **30Hz** 全量状态（3 个圆的位置/速度 + 过载计时）；帧 v 单调递增 |
| `event` | `{ type: "goal"\|"save"\|"foul_pushback", side, t }` | 事件流（客户端播粒子/音效/飘字） |
| `phase` | `{ state: "countdown"\|"playing"\|"point"\|"over", score:[a,b] }` | 阶段机 |
| `peer` | `{ event: "joined"\|"left"\|"reconnected" }` | 对局状态 |
| `error` | `{ code, message }` | |

### 2.3 服务端权威仿真（`TickEngine`）

- **固定步长 30Hz**（单房间一个任务，共享 `ScheduledExecutorService`；每 tick：
  ① 应用双方最新 input 力向量（输入缓存：每个 seat 存最近 1 帧 input，tick 间不变）
  ② 积分（半隐式欧拉：`v += f·dt·K; v *= friction; p += v·dt`）
  ③ 碰撞（puck↔弹珠 圆-圆弹性碰撞 e=0.9；弹珠↔壁 反射；puck↔口袋判定：圆心入袋口圆 r=28）
  ④ 半场约束（越界推回 + 硬直计时）⑤ 进球判定 → `event.goal` + 复位倒计时 2s。
- **物理纯函数化**（`Physics.step(state, inputs) → state`）：确定性 + 可单测（碰撞表驱动：
  正碰/斜碰/多球同帧/角落，断言能量不增 + 位置不变量）；`seed` 开局下发仅用于回放/调试复现。
- 时钟纪律：tick 用 `System.nanoTime()` 累积误差 > 1 tick（>33ms）时**跳 tick 补偿**（不追帧，
  直接前进——对战场景丢 1 帧可接受，螺旋死亡不可接受）。

### 2.4 客户端渲染（插值 + 本地预测）

- **插值**：服务端 snapshot 缓冲，渲染时点 = `now - 100ms`（取相邻两帧插值）——100ms 延迟
  在气垫球手感里不可感知，换来对抖动的免疫；
- **本地预测（只预测己方）**：己方 input 立刻本地积分渲染（手感 0 延迟），收到 snapshot 后
  己方位置误差 > 4px → **橡皮筋修正**（8 帧内线性归位）；puck/对方弹珠**纯插值不预测**
  （避免预测冲突的复杂回滚）；
- 断线重连：WS 断开 → 指数退避重连（1/2/4s ×3）→ 重连成功发 `resync{v}` → 服务端回最新
  snapshot + 相位；30s 未回 → 对局判负（`phase.over{reason:"disconnect"}`）；
- 客户端**永不**相信自己的渲染是权威：得分/事件以服务端 `event`/`phase` 为准（红线：同排行榜，服务端裁决）。

## 3. 数据模型（M5 新增）

```sql
CREATE TABLE duel_room (
  id           BIGSERIAL PRIMARY KEY,
  code         TEXT NOT NULL UNIQUE,      -- 6 位码（去易混字符 0O1I）
  host_user_id BIGINT,                    -- sysou-manage 用户 id
  status       TEXT NOT NULL DEFAULT 'open', -- open | playing | finished | abandoned
  score_a      INT NOT NULL DEFAULT 0,
  score_b      INT NOT NULL DEFAULT 0,
  winner_seat  SMALLINT,                  -- 0/1，finished 后写
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  finished_at  TIMESTAMPTZ
);
```

Redis：`room:<code> → {nodeId, status, ts}`（TTL 1h，finished 后 24h 供查询历史）。

## 4. 安全与滥用

| 面 | 对策 |
|---|---|
| 输入洪泛 | 每连接 `input` ≤ 30/s（Redis 滑窗限流，01 文档 §2.2 同款），超限丢帧 + 连续 10s 超限 → 断连罚下 |
| 作弊 | 权威服务端（位置/分数/事件全服务端算）；客户端上传只有力向量；无客户端物理 → 无本地作弊面 |
| 恶意断连刷分 | 断连判负 + 单用户每小时开局次数上限（10 局/小时，Redis 限流）；对局 < 30s 判负不计入榜单 |
| WS 洪泛/大包 | 帧 ≤ 2KB（Spring `maximumMessageSize`），超限断连；连接数按 JWT 用户去重（同用户多连接踢旧） |
| 内容 | 无文本聊天（M5 不做 chat，杜绝内容审核面；房间码本身就是唯一「社交」） |

## 5. 性能与容量

| 项 | 目标 |
|---|---|
| 服务端 tick 预算 | 单房间 30Hz，单核 < 1ms/tick（纯几何运算）⇒ 单 JVM 500 并发房间余量 |
| 网络 | snapshot 每帧 ~120B → 3.6KB/s/连接；30Hz 下 100 并发连接 ≈ 1.2MB/s 出网（VPS 无压力） |
| 首玩 | 包体 ~2MB（Canvas + 代码 + 音频），首玩 ≤ 5s；对战体验目标 RTT 容忍 ≤ 150ms（>200ms 开局提示「网络较卡」） |
| 帧率 | 渲染 60fps（Canvas 2D，3 圆 + 特效粒子 ≤ 100） |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 高 RTT（玩家跨地域）体验差 | 100ms 插值 + 己方预测（§2.4）；开局 RTT 检测 >200ms 提示；不做预测回滚（复杂度 vs 品类收益不匹配） |
| 单 JVM 房间状态重启丢失 | M5 接受（对战中断判平，重开）；Redis 只存索引；「断线 30s 内重连恢复」靠 JVM 内房间保活，不跨重启 |
| WebSocket 经 nginx 的坑（upgrade/超时/缓冲） | 01 文档 §8 片段 + 部署后 `wscat` 端到端验收；`proxy_buffering off` 必配 |
| 物理手感调不好（气垫球类手感吃参数） | `Physics` 参数（摩擦/弹性/力增益）全部配置化 + 本地「双人热座调试模式」（单机双客户端模拟，调参不用等对手） |
| 二期资源挤占一期 | M5 严格排在 M4 后；M1–M4 的 `duel` 模块**零占位**（不写死代码，避免技术债） |
