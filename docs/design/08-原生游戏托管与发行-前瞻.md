# 08 · 原生（非浏览器）游戏托管与发行设计（前瞻规划）

> 状态：**前瞻规划**——不在 M1–M5 排期；触发条件见 §2。触发启动时，本文档是该方向的唯一真源。
> 背景问题：平台当前设计是浏览器试玩（02 文档的游戏包规范以「纯静态 + 浏览器执行」为前提）。
> 若未来出现中大型复杂游戏（重 3D 场景 / 大体积音频 / 复杂 AI，Web 承载吃力或体验上限不够），
> 需要在本平台**发布、宣传、下载**原生版本（Windows / macOS / Linux）。本文回答怎么提前规划、
> 启动时怎么落地、哪些现在就该零成本预留。

---

## 1. 结论先行

1. **平台核心与载体无关，已被验证为可复用**：目录、详情页、排行榜、成就、遥测、管理台、
   sysou-manage 认证——全部只认「游戏内容 + 玩家 + 分数」，不感知游戏跑在浏览器还是原生二进制。
   原生游戏需要的四件事里，**托管（内容展示）、宣传、计分/成就已经就绪，唯独「分发（下载 + 更新）」要新增**。
2. **架构动作只有一个核心**：把 `game_version`（当前隐式 = web 版本）拆成
   「版本（元数据）+ 构建（载体）」。同一版本可同时挂 web / win / mac / linux 多个构建，
   各自独立发布、回滚（V2 迁移 SQL 见 §3）。
3. **下载 = 静态文件服务 + 完整性校验 + 代码签名**。nginx 原生支持 Range 断点续传，个人 VPS
   阶段零新组件；超阈值（§9）再上 CDN（URL 是相对路径，切 CDN 只换域不改协议）。
4. **刻意不做**（与平台红线一致）：DRM/加密狗/在线激活、账号库与自动同步推送（N3 默认不做；
   **云存档已提前进 M3**——01 文档 §5.2，属玩家基础体验而非「账号中心」）、
   第三方/他人游戏分发（MVP 红线是「自研游戏」，开放第三方需重审授权与内容责任）、付费。
5. **web-first 不动摇**：所有原生能力是**增量**（additive），M1–M5 的任何行为不改一行；
   每款游戏默认先出 web 版能玩，原生版是「体验上限不够时的升级通道」。

## 2. 触发条件（什么时候启动，而不是什么时候做完）

**触发 = 出现一款具体的「Web 版承载不足」的自研游戏**，不是排期驱动。判据（满足其一即启动 N1）：

- 完整体验包体 > 500MB（web 加载劝退线，远超 02 文档 100MB 包约束）；
- 需要 Web 给不了的体验（复杂 3D + 大型音频资产 + 高画质粒子/后处理，WebGPU 回退后差距明显）；
- 目标用户主动要「下载版」（运营反馈）。

**最自然的候选**：游戏 C 系（Godot）的后续大型项目 —— Godot 是平台五款游戏里唯一
**一套代码同时导出 web + win/mac/linux 原生**的引擎（05 文档选 Godot 的隐含收益在此兑现）。
若未来大型游戏改用 Unity 等，分发设计不变（§3–§6 与引擎无关），只是导出流程不同。

阶段划分：

| 阶段 | 内容 | 再触发条件 |
|---|---|---|
| **N0（现在做，成本 ≈ 0.5 天）** | §8 的零成本预留（schema 字段 + API 形状 + nginx 位置注释） | 无，随 M1 顺手落 |
| **N1（触发后 ~2–3 周）** | game_build 载体拆分 + 管理台构建上传 + 下载页 + 客户端 SDK + 代码签名 | §2 触发条件 |
| **N2（N1 后按需 ~2 周）** | 增量更新（整包 diff / 资源分包）+ 启动自动更新 | 单包 > 500MB 或月更 ≥ 1 次 |
| **N3（默认不做）** | 账号库 / 账号系其他扩展（云存档已提升进 M3；跨设备成就同步由服务端天然满足——成就本就在服务端判定） | 有真实玩家需求 + 明确愿意投入，否则不做 |

## 3. 数据模型演进：内容 / 版本 / 载体三层

**现状（M1–M5）**：`game`（内容）→ `game_version`（web 版本，`entry_url` 即 web 载体）。

**N1 演进**：`game_version` 保留为纯版本元数据，新增 `game_build` 表表达「这个版本以什么载体分发」：

```sql
-- V2__native_builds.sql（N1 启动时落，随 Flyway 版本走）
CREATE TABLE game_build (
  id              BIGSERIAL PRIMARY KEY,
  game_version_id BIGINT NOT NULL REFERENCES game_version(id),
  platform        TEXT NOT NULL,          -- web | windows | macos | linux
  arch            TEXT NOT NULL DEFAULT 'universal',   -- x86_64 | arm64 | universal
  type            TEXT NOT NULL,          -- static(web 静态包) | portable-zip | installer
  url             TEXT NOT NULL,          -- web: /game/g/<slug>/<ver>/ ；native: /game/dl/<slug>/<ver>/<file>
  size_bytes      BIGINT NOT NULL,
  sha256          TEXT NOT NULL,          -- 下载完整性（客户端 SDK 与页面展示都用它）
  signature       TEXT,                   -- 签名说明：Authenticode thumbprint / DeveloperID 证书 / GPG .sig URL
  notes           TEXT,                   -- 该载体特有说明（如「Win10 1903+」）
  status          TEXT NOT NULL DEFAULT 'staged',   -- staged | live | rolled_back（与版本状态联动）
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (game_version_id, platform, arch)
);
CREATE INDEX idx_build_live ON game_build (status) WHERE status = 'live';
```

**回填迁移**（数据不丢，M1–M5 已发布游戏无损）：

```sql
INSERT INTO game_build (game_version_id, platform, type, url, size_bytes, sha256, status)
SELECT id, 'web', 'static', entry_url, size_bytes, package_sha256, status
FROM game_version;
```

**兼容策略**：M1–M5 代码继续读写 `game_version.entry_url`（web 构建的别名视图），
N1 起详情页 API 增返 `builds[]`（§5.2），前端按 `builds` 渲染 CTA：
有 web → 「立即试玩」；有 native → 「下载 Windows / macOS 版」（双 CTA 并列）。
`game_version` 的 `entry_url` 字段在 N1 后只作 web 构建冗余缓存，读路径切到 `game_build`。

**发布语义**：版本与构建**解耦发布**——`1.2.0` 可以 web 先行（热修）而 native 后发
（需签名/公证流水线），`publish` 动作从「版本级」细化为「版本 × 构建」级；回滚同理
（web 回滚不影响 native 在线版）。

## 4. 下载服务（nginx + 存储）

```
/var/www/gamevault/downloads/<slug>/<version>/
├── <slug>-<version>-windows-x86_64.zip        # 便携包（首选：无安装器 = 无 UAC = 用户信任成本低）
├── <slug>-<version>-windows-x86_64.zip.sha256
├── <slug>-<version>-windows-x86_64.zip.sig    # 可选 GPG 签名（面向进阶用户）
├── <slug>-<version>-macos-universal.zip
└── <slug>-<version>-linux-x86_64.zip
```

nginx（N1 启用，插入 01 文档 §8 片段预留位，作用域在 `/game/` 前缀内）：

```nginx
location ^~ /game/dl/ {
    alias /var/www/gamevault/downloads/;
    try_files $uri =404;
    expires 30d;                          # 版本化 URL ⇒ 长缓存安全
    add_header Cache-Control "public";
    add_header Content-Security-Policy "default-src 'none'";   # 下载目录不可能是页面
    # Range 请求：nginx 静态文件原生支持（206 Partial Content），断点续传零代码
}
```

要点：

- **断点续传**：nginx 静态文件原生 Range，前端用 `<a href>` 直下或 JS `fetch` 分段下载
  （管理台上传用分块 multipart + Redis Streams Job 落盘，01 文档 §2.1 Job 框架复用，
  新增 Job 类型 `GAME_BUILD_UPLOAD`，单包上限 **2GB**，`client_max_body_size` 仅 `/game/api/admin/` 放宽）。
- **存储选型**：单 VPS 磁盘起步；单游戏 > 1GB 或多游戏并存时，走 VPS 上已有 S3 兼容对象存储
  （EasyPCB 已验证的 MinIO/R2 经验，跨工程复用 VPS 中间件属红线允许面），nginx 用 `X-Accel-Redirect`
  代理回源或直接 `proxy_pass` 到对象存储——**对浏览器仍是 `/game/dl/...` 同一 URL，协议不变**。
- **带宽（最大现实成本）**：200MB 游戏 × 1000 次下载 = 200GB 出网。个人 VPS 带宽包是硬约束 ⇒
  CDN 触发线见 §9（触发后 `/game/dl/` 指向 CDN 域名，源站配置不变）。
- **COOP/COEP**：`/game/dl/` 位于 `/game/` 前缀下会带上这两头——对纯下载无副作用，无需特判
  （01 文档 §8 作用域隔离的验收项补一条：`/game/dl/` 响应带 COOP/COEP 属预期）。

## 5. API 与客户端 SDK（复用现有契约，新增最小面）

### 5.1 现有 API 原样复用（一行不改）

分数提交 `POST /api/scores`、成就 `GET /api/me/achievements`、遥测 `POST /api/telemetry`、
榜单 `GET /api/games/{slug}/leaderboard`——全部是「REST + 中心 JWT」，与游戏跑在哪无关。
**这就是「内容与载体分离」在 API 层的兑现**：原生客户端与 web 游戏打的是同一套接口。

### 5.2 N1 新增端点

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/games/{slug}`（扩展） | 响应增 `builds: [{platform, arch, type, url, sizeBytes, sha256, signature, notes}]`（M1–M5 恒为仅 web 一条，前端已有兼容） |
| GET | `/api/games/{slug}/latest-build?platform=&arch=` | 客户端启动时查（自动更新用）；404 = 该平台无构建 |
| POST | `/api/admin/versions/{id}/builds` | 管理台上传构建（分块）→ `GAME_BUILD_UPLOAD` Job → 校验（大小/sha256/签名文件在位）→ staged |
| POST | `/api/admin/builds/{id}/publish` | 按「版本 × 构建」发布（§3 语义） |

### 5.3 原生客户端 SDK（~300 行，一个小型库，Godot/Unity 各包一层薄适配）

| 能力 | 实现 |
|---|---|
| 登录 | 打开系统浏览器 → sysou-manage 登录页（带 `redirect_uri=http://127.0.0.1:<随机端口>/cb`）→ 客户端本地 loopback 监听收 code → 换 JWT 存 OS 密钥库。若中心 OAuth 尚未支持该流程，N1 降级方案：页面显示 8 位临时码，用户回游戏内输入（管理台签发，5 分钟有效）——以 sysou-manage 当时能力为准（红线：以官方/现状为准） |
| 提分/成就/遥测 | 直接调 §5.1 现有 API（Godot: `HTTPRequest`；Unity: `UnityWebRequest`）；**不写死域名**：用启动时注入的 `platformBase`（打包时从构建配置读，默认同源推导） |
| 自动更新 | 启动 `GET latest-build` → 对比本地 `BUILD_INFO.json`（version + sha256）→ 不一致提示「有新版本」；N1 整包重下，N2 走增量（§7） |
| 完整性 | 下载完成校验 sha256（页面与 SDK 同一真值），失败提示重下 |
| 崩溃遥测（可选） | 结构化崩溃报告走 `/api/telemetry`（`type:"crash"`，含 OS/版本/摘要，**不含用户路径与隐私**） |

### 5.4 反作弊（原生比浏览器攻击面大，策略收紧而非放松）

- 服务器权威原则不变：分数/成就只认服务端校验链（01 文档 §6.1 全套复用：限流 → schema →
  时间合理性 → 异常检测）。
- **差异**：web 游戏运行在平台 iframe 内（受信任自研代码 + 同源 API），原生二进制在玩家机器上
  可被篡改 ⇒ 对 `platform≠web` 的提交默认走 **flagged 人工复核队列**（01 文档 §6.1 第 5 步的
  异常检测阈值对 native 收紧：P99×3 即 flag），复核确认后进榜。
- 不做本地检测/DRM（个人平台量级无意义）；信任锚 = sha256 + 代码签名 + 服务端裁决三件套。

## 6. 代码签名与信任（一次性成本清单）

| 平台 | 要求 | 成本/年（量级，以官方当前价为准） |
|---|---|---|
| Windows | Authenticode 代码签名证书（EV/OV）+ 签名；新用户首次运行过 SmartScreen「更多信息」属正常，签名后随安装量累积信誉 | 数百元 |
| macOS | Developer ID 证书 + **notarization**（苹果公证），否则 Gatekeeper 全拒 | Apple $99 |
| Linux | 无强制签名；附 GPG 签名文件 + sha256 供验证 | 0 |

- 签名在**构建侧**完成（本地/CI，与 05 文档「Godot 构建在本地、VPS 只收静态包」同纪律）；
  VPS 永不接触私钥（红线：密钥不进仓库——签名证书私钥同理只进构建机密钥库）。
- 下载页明示签名状态与校验方式（「本文件已 Authenticode 签名，指纹 …；sha256 …」）——
  **宣传与信任同一件事**，写进详情页模板。

## 7. 更新策略（N2）

- N1 期：整包重下（简单、正确、有 sha256 兜底）。
- N2 触发后：两种可选路径，按包体构成选——
  1. **整包 binary diff**（xdelta 类工具生成补丁，客户端 `patch(旧, 补丁) → 新` + sha256 校验）：
     适合「代码变更多、资产变更少」；
  2. **资源分包**（引擎代码包 + 资产包分离，资产包独立版本号，Godot 的 `.pck` 天然支持热替换）：
     适合「资产迭代为主」的项目。
- 自动更新 = SDK §5.3 的 `latest-build` 轮询 + 用户确认后执行（**永不静默替换运行中二进制**，
  Windows 文件锁问题用「提示重启」解决，不造服务）。

## 8. 零成本预留（N0，随 M1 顺手落进 01 文档）

1. **`game` 表加 `media JSONB`**（宣传面现在就长出来）：
   `{"screenshots": ["/game/g/<slug>/shots/01.png"], "trailer": "…mp4 URL", "external_links": [{"name":"Steam 页","url":"…"}]}`
   —— 详情页模板 N1 前就可展示截图墙/预告片；`external_links` 支持「本平台不托管、只宣传导流」
   （如游戏同时在 Steam/itch.io 发布）——零运行时成本。
2. **API 响应形状预留**：`GET /api/games/{slug}` 恒带 `builds: []`（M1–M5 填 web 一条，或留空
   由前端按 `entry_url` 兜底）——N1 只填数据，不改形状。
3. **nginx 位置注释预留**：01 文档 §8 片段中留 `/game/dl/` 注释块（不启用），N1 取消注释 + 建目录。
4. **管理台页面结构**：游戏详情页预留「构建」Tab 占位（M1 显示「仅 web 构建」），N1 激活。

> 以上 4 项合计 ≈ 0.5 天工作量，换来 N1 启动时**零数据迁移之外的结构改动**（V2 迁移只做
> game_version → game_build 拆分，数据回填是机械操作）。

## 9. 路线图与成本/带宽纪律

| 项 | 纪律 |
|---|---|
| 单包上限 | N1 期 ≤ 2GB（存储/上传现实约束）；> 500MB 时强制 N2 分包评估 |
| 带宽告警 | 出网带宽包用量 > 50% 或单月下载量 > 500GB（取先到）⇒ **强制上 CDN**（`/game/dl/` 换 CDN 域名，协议/URL 结构不变）；CDN 成本转嫁前，下载页明示体积 |
| 构建矩阵 | 个人项目只承诺：**Windows（Win10 22H2+/Win11，x86_64）+ macOS（近两个大版本，universal）+ Linux（x86_64，主流发行版）**；页面明示最低要求，不做考古兼容 |
| 签名 | N1 起 Windows/macOS 构建**必须**签名/公证才允许 publish（管理台校验 signature 字段非空，否则发布按钮禁用——与「待确认清单」同款闸门思路） |
| 第三方游戏 | **默认拒绝**（自研红线）。若未来要分发他人游戏：先过授权证明 + 内容审核清单 + 法律免责评估，再开新红线评审，**不在这条流水线里顺手做** |

## 10. 风险汇总

| 风险 | 影响 | 对策 |
|---|---|---|
| 个人 VPS 带宽被大包下载打穿（影响 /game/ 全部服务） | 高 | 带宽告警 + CDN 触发线（§9）；极端情况 nginx 对 `/game/dl/` 限流（`limit_rate`）保 API 与 web 游戏 |
| SmartScreen/Gatekeeper 拦截导致「病毒」差评 | 中 | 签名 + 公证 + 下载页信任说明（§6）；首发期在详情页放「为什么弹提示」FAQ |
| 原生客户端篡改分数 | 中 | native 提交默认 flagged 人工复核（§5.4）；榜单位公示「原生分数经人工核验」 |
| 多平台测试矩阵膨胀 | 中 | 构建矩阵收缩到 §9 承诺线；每台 OS 一台主力机 + CI（GitHub Actions 多 runner 导出三平台，05 文档导出脚本同款扩展） |
| game_version → game_build 迁移影响 M1–M5 已上线功能 | 低 | 兼容视图 + 回填脚本 + 迁移后回归 02 文档 §8 验收清单（迁移本身是机械 SQL，风险在回归不在 SQL） |
| 前瞻设计过度膨胀（YAGNI） | 中 | N0 只做 4 项零成本预留；N1 代码**一行不提前写**（模块清单 01 文档 §2 不预建 native 模块） |
